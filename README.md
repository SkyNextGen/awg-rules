# AWG Rules — моя памятка

**Моя схема** — Keenetic с AWG Manager → sing-box в режиме TProxy → удалённый набор `routing.srs` → выбранный AWG-туннель для трафика из набора.

[Последняя публикация](dist/report.md) · [Запуски GitHub Actions](https://github.com/SkyNextGen/awg-rules/actions/workflows/build.yml) · [Состав источников](config/sources.json)

## Настройка AWGM

1. В маршрутизации sing-box добавляю удалённый набор (`remote`) формата `binary`. Вставляю URL подписки:

   ```text
   https://raw.githubusercontent.com/SkyNextGen/awg-rules/main/dist/routing.srs
   ```

2. Создаю правило, которое направляет совпадения с этим набором в нужный AWG-туннель. Применяю конфигурацию и проверяю, что устройство попадает под перехват TProxy.
3. Задаю интервал обновления **у этого удалённого набора**. Он определяет, когда sing-box проверит ссылку. Сборка на GitHub идёт по своему расписанию.
4. В настройках движка sing-box выбираю **«Оперативная память (/tmp)»** для файла кэша. Это настройка кэша движка, где может храниться и скачанная копия SRS.

Для новой установки использую движок, поставляемый с актуальной AWGM. Версия компилятора, указанная в настройках сборки репозитория, относится к созданию файла SRS. Совместимость движка проверяется отдельно в CI.

Если понадобится **DNS-маршрутизация Keenetic/NDMS**, её подписка — [routing.txt](https://raw.githubusercontent.com/SkyNextGen/awg-rules/main/dist/routing.txt). В TXT есть домены и IP, а отдельные условия Discord по UDP-портам доступны в SRS. [JSON](dist/routing.json) удобно читать при проверке содержимого набора.

## Обновление списка вручную

В моей настройке AWGM кнопки «обновить набор сейчас» нет. Когда ждать интервала неудобно, обновляю так:

1. Открываю [отчёт сборки](dist/report.md) и сверяю дату сборки с [последней публикацией](https://github.com/SkyNextGen/awg-rules/commits/main/dist/report.md). Если GitHub ещё собирает список или последняя проверка упала, по текущей ссылке доступна предыдущая публикация.
2. Перезагружаю Keenetic. Кэш в `/tmp` очищается при перезагрузке роутера. При обычном перезапуске sing-box файл может сохраниться, и движок снова подхватит старый набор.
3. Когда роутер и туннель поднимутся, смотрю журнал AWGM. Проверяю, что sing-box успешно запустился и удалённый набор загрузился. Для новой загрузки ссылка должна быть доступна с роутера. Затем открываю нужный сервис и проверяю в журнале соединений, что трафик ушёл через выбранный туннель.

## Если что-то не работает

| Что вижу | Что проверяю |
|---|---|
| В Telegram пришла ошибка сборки | Читаю причину и строку о публикации. Если состояние списка не удалось подтвердить, открываю [отчёт](dist/report.md) и [журнал запуска](https://github.com/SkyNextGen/awg-rules/actions/workflows/build.yml). Красный запуск сам по себе не говорит, какой файл сейчас использует роутер. |
| Сборка успешна, но в Telegram есть предупреждение | Смотрю, какие данные вошли в итог. Например, часть сетей могла остаться из проверенной копии. Затем сверяю время отчёта и проверяю, загрузил ли AWGM этот набор. |
| AWGM не загружает SRS после перезагрузки | В журнале ищу ошибку скачивания или чтения файла. Сверяю URL, тип `remote`, формат `binary` и доступ роутера к GitHub по маршруту, выбранному для скачивания. |
| SRS загрузился, но соединение идёт напрямую | В журнале соединений смотрю адрес назначения, сработавшее правило и выход. Проверяю, применяется ли правило к устройству и не срабатывает ли раньше обход. Для доменных совпадений проверяю, видно ли имя через DNS или распознавание трафика. |
| WhatsApp или Telegram открывается, но звонок или вложение не работает | Отдельно воспроизвожу звонок, загрузку файла и просмотр медиа. Смотрю именно эти соединения, их IP, протокол и выход. Если на том же устройстве через полный VPN всё работает, начинаю с проверки выборочной маршрутизации. |
| В Discord чат работает, а аватарки или голос — нет | Проверяю эти сценарии раздельно. Для медиа проверяю обращения к CDN, для голоса — перехват UDP, IP и порт назначения. Высокий порт в графе «Источник» может быть обычным временным портом устройства. |
| В журнале только IPv4 | Проверяю, есть ли у устройства рабочий IPv6, перехватывается ли он роутером и поддерживает ли его выбранный выход. Само наличие IPv6 в SRS не включает эти настройки. |

**Быстрый откат в AWGM.** В [истории `routing.srs`](https://github.com/SkyNextGen/awg-rules/commits/main/dist/routing.srs) выбираю известный рабочий коммит и заменяю `main` в URL подписки на его SHA. После применения проверяю загрузку и повторяю сломавшийся сценарий. Когда актуальная публикация проверена, возвращаю URL с `main`.

**Когда решу сделать репозиторий закрытым.** Сначала проверяю, откуда AWGM сможет скачивать SRS без ручного входа в GitHub. Текущая схема опирается на открытый raw-URL. Перед сменой видимости проверяю новый способ доставки с роутера, в том числе после очистки кэша. Адрес записываю здесь, ключи и токены в README не добавляю.

### Цель и принятые решения

Личный репозиторий для выборочной маршрутизации. Основной результат — один общий SRS для моей схемы AWGM/TProxy. TXT нужен для отдельного сценария NDMS. Три JSON в `dist/custom/` помогают проверять состав Telegram, WhatsApp и Discord. При аудите меня прежде всего интересуют звонки, файлы и медиа WhatsApp и Telegram, а также голос и аватарки Discord.

- **Meta и WhatsApp.** Используются RIPEstat по выбранным ASN, два geofeed Meta, списки ITDog IPv4/IPv6, MetaCubeX и Loyalsoldier. В проверенных исторических сборках подсети Meta от ITDog перекрывались RIPEstat и официальными geofeed, но я решил пока оставить оба списка. Точные IP известных CDN WhatsApp заново собираются через DoH. Ответы зависят от точки запроса и могут отличаться от DNS на роутере.
- **Discord.** Сборщик читает опубликованный `discord.srs` ITDog, сверяет SHA256, дату и покрытие IPv4 с отдельным списком ITDog. Для основного голосового правила используется также отдельный IPv6-список. IPv4 Cloudflare и голосовые диапазоны остаются в правилах с условиями «UDP + сеть + порт назначения». Личные дополнения лежат в `config/custom-discord-voice.json`. Адреса CDN для медиа ограничены TCP/UDP 443.
- **Разделение условий.** Общие доменные и IP-условия находятся в отдельных элементах SRS. Это важно для сопоставления DNS в AWGM. TXT включает поддомены, в том числе для перенесённых точных доменов, и пропускает условия по портам, ключевым словам и регулярным выражениям.
- **Отказ источников.** Для BGP есть резервный bgp.tools и ограниченный по возрасту снимок. Для списков Meta при сетевой ошибке допускается проверенный снимок в пределах срока. Для DNS предыдущие адреса не подмешиваются. Состояние плановых сборок ITDog отражается в предупреждениях, а сами данные проходят независимые проверки.

### С чего начать аудит

1. Зафиксировать SHA проверяемого коммита и версию движка AWGM. Прочитать инструкции репозитория, если они есть. Проверить, что локальные изменения владельца сохраняются.
2. Сопоставить `config/`, `dist/source-snapshot.json` и итоговые правила одного коммита. Сравнивать фактическое покрытие адресов IPv4 и IPv6, а не только число CIDR. При проверке Discord учитывать сеть, протокол и порт вместе.
3. Проверить отказ источника, допустимость и срок резерва, полноту DNS, пределы роста/сокращения покрытия и порядок публикации. Отдельно проверить, что Telegram объясняет последствия сбоя и подтверждает состояние списка перед сообщением о сохранении старой версии.
4. Прогнать тесты и контрольную пересборку. Для проверки сетевых источников использовать отдельный checkout. Обычный запуск сборщика там запишет результаты в его локальный `dist/`.

```sh
python3 -m unittest discover -s tests -v
python3 src/install_sing_box.py
python3 tests/replay_build.py --baseline . --sing-box .tools/sing-box
python3 src/check_service_coverage.py
```

Команды приведены для Linux с Python 3.12. Для replay базой служит опубликованный checkout, в котором настройки и `dist/` относятся к одной публикации. Если конфигурация изменена локально, передать путь к отдельному опубликованному checkout. Replay проверяет воспроизведение SRS, JSON, TXT и JSON сервисов на сохранённых входах. Актуальность внешних источников и поведение конкретного роутера проверяются отдельно. Команды для прогонов на sing-box и awgm-box указаны в [workflow](.github/workflows/build.yml).
