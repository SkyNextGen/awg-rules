## Подключение

**Схема маршрутизации:** Keenetic с AWG Manager → sing-box в режиме TProxy → правила из `routing.srs` → выбранный AWG-туннель.

1. В настройках маршрутизации sing-box добавить удалённый набор (`remote`) в формате `binary`. URL подписки:

   ```text
   https://raw.githubusercontent.com/SkyNextGen/awg-rules/main/dist/routing.srs
   ```

2. Создать правило, которое направляет совпавший трафик в нужный AWG-туннель. После применения убедиться, что устройство входит в область перехвата TProxy.
3. Задать интервал обновления у удалённого набора. По нему sing-box проверяет URL подписки. GitHub собирает и публикует список по отдельному расписанию.
4. Для файла кэша sing-box выбрать **«Оперативная память (/tmp)»**. В этом кэше может храниться скачанная копия SRS.

Для DNS-маршрутизации Keenetic в режиме NDMS используется [routing.txt](https://raw.githubusercontent.com/SkyNextGen/awg-rules/main/dist/routing.txt). В TXT входят домены и IP-подсети. Отдельные правила Discord с ограничениями по протоколу и портам доступны в SRS. Для просмотра содержимого SRS есть [routing.json](dist/routing.json).

## Ручное обновление

Если в используемой версии AWGM нет кнопки принудительной загрузки SRS, набор можно обновить перезагрузкой Keenetic при хранении кэша в `/tmp`.

1. Перед перезагрузкой убедиться, что новый список уже опубликован. Дата сборки указана в [отчёте](dist/report.md), а публикация видна в [истории SRS](https://github.com/SkyNextGen/awg-rules/commits/main/dist/routing.srs).
2. Перезагрузить роутер. При перезагрузке Keenetic кэш в `/tmp` очищается. При перезапуске только sing-box файл кэша может сохраниться.
3. После запуска роутера и туннеля проверить в журнале AWGM, что sing-box запустился и загрузил удалённый набор. Для повторного скачивания URL подписки должен быть доступен с роутера.
4. Открыть нужный сервис и проверить в журнале соединений AWGM, что трафик идёт через выбранный туннель.

## Диагностика

| Симптом | Что проверить |
|---|---|
| В Telegram пришла ошибка сборки | Уведомление показывает причину и сообщает, подтверждено ли сохранение прежней публикации. Если статус списка неизвестен, сверить [отчёт](dist/report.md) и [запуск GitHub Actions](https://github.com/SkyNextGen/awg-rules/actions/workflows/build.yml). Версию, загруженную на роутере, проверить отдельно в AWGM. |
| Сборка успешна, но в Telegram есть предупреждение | В [отчёте](dist/report.md) указано, какие данные попали в итоговый список. Например, при сбое источника могла использоваться проверенная копия. Сверить дату публикации и проверить загрузку набора в AWGM. |
| AWGM не загружает SRS после перезагрузки | Проверить URL, тип `remote`, формат `binary` и доступ роутера к GitHub через выбранный выход для скачивания. Ошибка скачивания или чтения файла отображается в журнале AWGM. |
| SRS загрузился, но соединение идёт напрямую | Сверить адрес назначения, сработавшее правило и выход в журнале соединений. Проверить перехват устройства, порядок правил и доступность имени назначения для доменного совпадения. |
| WhatsApp или Telegram открывается, но звонок или вложение не работает | Проверить звонок, передачу файла и загрузку медиа отдельно. Для проблемного подключения сверить IP назначения, протокол и выход. Если тот же сценарий работает через полный VPN, начать с правил выборочной маршрутизации. |
| В Discord работает чат, но не грузятся аватарки или не работает голос | Для аватарок проверить подключения к CDN. Для голоса — перехват UDP, IP и порт назначения. Высокий порт в графе «Источник» может быть временным портом устройства. |
| В журнале только IPv4 | Проверить IPv6 на устройстве, перехват IPv6 на роутере и поддержку на выбранном выходе. Наличие IPv6-адресов в SRS само по себе не включает перехват. |

### Откат списка

В [истории `routing.srs`](https://github.com/SkyNextGen/awg-rules/commits/main/dist/routing.srs) выбрать рабочий коммит и подставить его SHA вместо `main` в URL подписки. Применить настройки, проверить загрузку и повторить проблемный сценарий. После проверки актуальной публикации вернуть URL с `main`, чтобы возобновить обновления.

### Доступ к подписке после закрытия репозитория

Текущая подписка использует открытый raw-URL GitHub. Перед переводом репозитория в приватный режим настроить доступный роутеру способ доставки SRS и проверить скачивание после очистки кэша. Адрес новой подписки можно указать в разделе подключения. Ключи и токены следует хранить отдельно.

### Цель и принятые решения

Личный репозиторий для выборочной маршрутизации. Основной результат — общий SRS для AWG Manager с sing-box в режиме TProxy. TXT нужен для отдельного сценария NDMS. Три JSON в `dist/custom/` помогают проверять состав Telegram, WhatsApp и Discord. Приоритетные сценарии для проверки — звонки, файлы и медиа WhatsApp и Telegram, голос и аватарки Discord.

- **Meta и WhatsApp.** Используются RIPEstat по выбранным ASN, два geofeed Meta, списки ITDog IPv4/IPv6, MetaCubeX и Loyalsoldier. В проверенных исторических сборках подсети Meta от ITDog перекрывались RIPEstat и официальными geofeed. Оба списка сохранены в конфигурации. Точные IP известных CDN WhatsApp заново собираются через DoH. Ответы зависят от точки запроса и могут отличаться от DNS на роутере.
- **Discord.** Сборщик читает опубликованный `discord.srs` ITDog, сверяет SHA256, дату и покрытие IPv4 с отдельным списком ITDog. Для основного голосового правила используется также отдельный IPv6-список. IPv4 Cloudflare и голосовые диапазоны остаются в правилах с условиями «UDP + сеть + порт назначения». Личные дополнения лежат в `config/custom-discord-voice.json`. Адреса CDN для медиа ограничены TCP/UDP 443.
- **Разделение условий.** Общие доменные и IP-условия находятся в отдельных элементах SRS. Это важно для сопоставления DNS в AWGM. TXT включает поддомены, в том числе для перенесённых точных доменов, и пропускает условия по портам, ключевым словам и регулярным выражениям.
- **Отказ источников.** Для BGP есть резервный bgp.tools и ограниченный по возрасту снимок. Для списков Meta при сетевой ошибке допускается проверенный снимок в пределах срока. Для DNS предыдущие адреса не подмешиваются. Состояние плановых сборок ITDog отражается в предупреждениях, а сами данные проходят независимые проверки.

### С чего начать аудит

1. Зафиксировать SHA проверяемого коммита и версию движка AWGM. Прочитать инструкции репозитория, если они есть. Проверить, что локальные изменения владельца сохраняются.
2. Сопоставить `config/`, `dist/source-snapshot.json` и итоговые правила одного коммита. Сравнивать фактическое покрытие адресов IPv4 и IPv6. Число CIDR использовать как дополнительный показатель. При проверке Discord учитывать сеть, протокол и порт вместе.
3. Проверить отказ источника, допустимость и срок резерва, полноту DNS, пределы роста/сокращения покрытия и порядок публикации. Отдельно проверить, что Telegram объясняет последствия сбоя и подтверждает состояние списка перед сообщением о сохранении старой версии.
4. Прогнать тесты и контрольную пересборку. Для проверки сетевых источников использовать отдельный checkout. Обычный запуск сборщика там запишет результаты в его локальный `dist/`.

```sh
python3 -m unittest discover -s tests -v
python3 src/install_sing_box.py
python3 tests/replay_build.py --baseline . --sing-box .tools/sing-box
python3 src/check_service_coverage.py
```

Команды приведены для Linux с Python 3.12. Для replay базой служит опубликованный checkout, в котором настройки и `dist/` относятся к одной публикации. Если конфигурация изменена локально, передать путь к отдельному опубликованному checkout. Replay проверяет воспроизведение SRS, JSON, TXT и JSON сервисов на сохранённых входах. Актуальность внешних источников и поведение конкретного роутера проверяются отдельно. Команды для прогонов на sing-box и awgm-box указаны в [workflow](.github/workflows/build.yml).
