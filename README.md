## 🚀 Подключение

### sing-box / TProxy — SRS

**1.** Добавьте удалённый rule-set в AWG Manager / sing-box.  
**2.** Выберите формат **binary** и укажите URL:

```text
https://raw.githubusercontent.com/SkyNextGen/awg-rules/main/dist/routing.srs
```

**3.** Направьте совпадающий трафик в нужный VPN outbound и включите обновление набора.

### NDMS — TXT

**1.** Создайте DNS-маршрут в разделе NDMS в AWG Manager.  
**2.** В «Подписки» добавьте URL:

```text
https://raw.githubusercontent.com/SkyNextGen/awg-rules/main/dist/routing.txt
```

**3.** Добавьте нужный AWG-туннель в маршрут и сохраните. Устройства должны использовать DNS роутера; DoH/DoT на самом роутере можно оставить. Для сравнения режимов отключите перехват маршрутизации sing-box, сохранив работающий туннель. Для штатной DNS-маршрутизации Keenetic устройство должно находиться в политике «По умолчанию».

В TXT находятся **домены, IPv4 и IPv6**, по одной записи на строку. Любой домен включает все поддомены; `*` не нужен. Точные условия SRS при переносе тоже становятся суффиксами. UDP-правила с портами, keyword и regexp исключены. [Документация Keenetic](https://support.keenetic.com/sprinter/kn-3711/en/51150-dns-based-routes.html) подтверждает включение поддоменов.

| [📦 routing.srs](https://raw.githubusercontent.com/SkyNextGen/awg-rules/main/dist/routing.srs) | [📄 routing.txt](https://raw.githubusercontent.com/SkyNextGen/awg-rules/main/dist/routing.txt) | [🔎 routing.json](dist/routing.json) | [📊 Отчёт](dist/report.md) |
|---|---|---|---|
| sing-box / TProxy | NDMS / DNS-маршруты | Полные правила SRS в читаемом виде | Статус, изменения и источники |

> Для доменных правил нужно определение имени через DNS/sniffing. В режиме TProxy сохраняйте UDP-порты Discord вместе с IP-условиями. Работу IPv6 и звонков проверяйте на своём устройстве.

## 🔄 Обновление и контроль

**Каждый день в 23:17 МСК** GitHub Actions выполняет сборку. Запуск также доступен вручную и после изменений кода или настроек. Возможны задержки расписания GitHub.

| ① Получение | ② Объединение | ③ Проверка | ④ Публикация |
|---|---|---|---|
| Загрузка доменов и IP | Удаление повторений, сокращение суффиксов и сетей | Тесты, формат SRS, покрытие TXT и сервисов | SRS и TXT одним коммитом; отчёт в Telegram |

**При ошибке проверки остаётся последний успешно опубликованный комплект SRS и TXT.** Оба файла создаются из одного снимка источников на каждом успешном запуске. Отчёт показывает изменения по источникам, дельты доменов и IP, а также динамику сборок. Ошибка доставки Telegram не отменяет публикацию.

### 1. Как устроена сборка

Все источники сводятся в один rule-set. Состав задаётся в `config/`, а готовые результаты создаются в `dist/`.

| Этап | Действие |
|---|---|
| Получение | Загрузка ITDog, категорий V2Fly, списков мессенджеров, официальных CIDR Telegram, BGP, Meta geofeed и DNS известных WhatsApp CDN |
| Нормализация | Проверка доменов и сетей, раскрытие вложенных категорий |
| Объединение | Удаление повторений, сокращение суффиксов и объединение CIDR |
| Голос Discord | Добавление отдельных правил с протоколом UDP и портами |
| Компиляция | JSON → SRS → JSON официальным sing-box |
| NDMS | Создание TXT из общих доменов и сетей; точные домены становятся суффиксами, портовые правила и keyword/regexp пропускаются |
| Контроль | Сравнение правил после обратного преобразования, сверка активных строк TXT с допустимым составом JSON и проверка сервисного покрытия |
| Публикация | Коммит всех результатов в `main`, затем уведомление в Telegram |

Сначала результат создаётся в промежуточной папке. После успешной компиляции и сравнения он переносится в локальный `dist`. GitHub публикует файлы только после дополнительной проверки покрытия. Ошибка до публикации сохраняет последнюю опубликованную версию.

### 2. Доменные правила и суффиксы

| Запись источника | Условие sing-box | Значение |
|---|---|---|
| `example.com` или `domain:example.com` в V2Fly | `domain_suffix` | Сам домен и все его поддомены |
| `full:example.com` | `domain` | Только указанное имя |
| `keyword:example` | `domain_keyword` | Совпадение по ключевому слову |
| `regexp:…` | `domain_regex` | Совпадение по регулярному выражению |
| `include:category` | Вложенные правила | Рекурсивное получение другой категории |

Записи `custom-domains.txt`, основного списка ITDog и дополнительных доменных списков ITDog обрабатываются как суффиксы. Имена приводятся к нижнему регистру, международные домены — к IDNA; завершающая точка и начальное `*.` удаляются. URL, IP и некорректные имена отклоняются.

**Пример объединения:**

| До | После | Покрытие |
|---|---|---|
| `google.com`, `clients6.google.com` | `google.com` | Google и его поддомены |
| `a.example.com`, `b.example.com` | Обе записи | Родитель `example.com` сам не добавляется |
| Suffix `example.com` + exact `a.example.com` | Suffix `example.com` | Точное правило уже покрыто |
| `example.com`, `notexample.com` | Обе записи | Разные доменные зоны |

Сокращение учитывает границы доменного имени. Общий родительский домен не выводится из нескольких поддоменов, поэтому само объединение не расширяет покрытие.

Вложенные категории кэшируются в пределах одной сборки; циклы и пустые категории отклоняются. Атрибуты обычных записей V2Fly не фильтруются: такие записи включаются. Фильтрованные `include` и неизвестные типы записей блокируют сборку, чтобы не менять их смысл молча.

### 3. IP-сети: источники и объединение

IP получаются независимо от доменных списков. DNS-адреса не превращаются в постоянные сети и не расширяются до ASN провайдера.

| Источник IP | Использование |
|---|---|
| Официальные CIDR Telegram | В общем наборе и отдельном наборе Telegram |
| BGP Telegram | В общем наборе и отдельном наборе Telegram |
| BGP Meta | В общем наборе и отдельном наборе WhatsApp |
| Личные CIDR | В общем наборе; задаются вручную |
| Подсети Discord ITDog | Только в отдельных правилах с UDP и портами |

Разрешённые ASN закреплены в сборщике:

| Группа | ASN |
|---|---|
| Telegram | `62041`, `62014`, `59930`, `44907`, `211157` |
| Meta | `32934`, `63293` |

Добавление другого ASN в конфигурацию требует изменения проверки в коде. Общие ASN Google, Cloudflare, Amazon и других CDN автоматически не включаются. Сети Meta принадлежат инфраструктуре компании и не выделяют исключительно трафик WhatsApp.

CIDR проверяются в строгом режиме: например, `1.1.1.1/24` отклоняется из-за ненулевой части адреса за пределами префикса. IPv4 и IPv6 объединяются отдельно. Вложенные сети удаляются, соседние объединяются только когда результат содержит ровно те же адреса.

```text
1.1.1.0/25 + 1.1.1.128/25 → 1.1.1.0/24
```

Отклоняются сети с неглобальным начальным или конечным адресом, а также слишком широкие префиксы: короче `/8` у IPv4 и `/19` у IPv6. Это защита от некорректного входа, а не доказательство принадлежности сети конкретному сервису.

### 4. BGP и резервные источники

BGP отражает наблюдавшиеся анонсы сетей, по умолчанию за последние две недели. Для Meta запрашиваются также префиксы с низкой видимостью (`min_peers_seeing=1`). Это не проверка доступности каждого адреса. В группе Meta используются AS32934, AS63293 и корпоративный AS54115. Сборщик последовательно использует:

1. **RIPEstat announced-prefixes** — основной источник для каждого ASN.
2. **bgp.tools/table.jsonl** — резервная таблица, загружаемая один раз для отсутствующих ASN.
3. **Предыдущий проверенный снимок** — если оба живых источника не дали допустимых данных.

Для каждого ASN нужны IPv4 и IPv6, непустой ответ и допустимый размер. При наличии предыдущего снимка количество объединённых префиксов сравнивается с ним.

Снимок принимается только при возрасте от 0 до **8 дней**. При его использовании исходная дата получения сохраняется. Переход на bgp.tools или снимок отображается в предупреждениях. Если допустимых данных нет, публикация останавливается.

Сборщик проверяет включение доменов и IP отдельных наборов в общий результат, а для Discord — сохранение UDP-правил с портами. Также проверяются ключевые домены Discord, Nexus Mods, Signal и официальный CIDR Telegram.

### WhatsApp: сети Meta и региональные CDN

`meta_ip_sources` в `sources.json` задаёт шесть IP-источников: два официальных geofeed, IPv4/IPv6 ITDog, MetaCubeX и Loyalsoldier. Все загружаются при каждой сборке. Для geofeed проверяется дата публикации: не более 8 дней и не в будущем. Для каждого списка проверяются число входных записей, строгие публичные CIDR и ожидаемые семейства адресов. Недоступный или некорректный источник останавливает публикацию; резервы BGP остаются отдельным механизмом.

`whatsapp_dns` задаёт список известных имён и получение их A/AAAA через `https://dns.google/resolve`, с резервом `https://cloudflare-dns.com/dns-query`. Принимаются только имена внутри проверенных корней WhatsApp и общей инфраструктуры Meta; похожие домены вроде `whatsapp.net.example.com` и неподтверждённый `wa.com` отбрасываются. В SRS имена сокращаются существующими суффиксами, поэтому тысячи известных поддоменов не превращаются в тысячи новых доменных правил.

HTTPS-транспорт запросов использует IPv4 с проверкой TLS-сертификата; это не исключает AAAA и IPv6 из результата. DNS проверяется в 24 потока, до трёх попыток на резолвер с таймаутом 10 секунд и общим пределом ожидания 600 секунд. Проверяются исходный DNS-вопрос, семейство IP, цепочка CNAME и публичность адреса. NXDOMAIN/пустой ответ не создаёт IP-правила. После неудачных попыток у обоих резолверов допускается не более 20 недоступных вопросов и не более 0,5% всех вопросов; их IP не добавляются, пропуски отмечаются предупреждением и сохраняются в снимке. Превышение любого порога, потеря семейства или слишком маленький результат блокирует сборку. Некорректный вопрос/ответ и непубличный IP блокируют сборку независимо от порога пропусков. Старые DNS-адреса не подмешиваются.

Нужно не менее 1000 допустимых имён источника, 500 имён с публичными IP и 100 уникальных IP; верхние границы — 10 000 имён и 6000 IP. Число имён, разрешившихся имён и IP должно оставаться в пределах 75–150% прошлого успешного DNS-снимка. Пороги выявляют резкие изменения, но не доказывают полноту списка.

Сохраняется `dist/whatsapp-dns.json`: время проверки, использованный резолвер, A/AAAA, TTL и статусы ответов. Точные адреса записываются как `/32` и `/128`; объединяются только реально смежные адреса без захвата отсутствующих соседей. Сети провайдеров целиком не добавляются. Эти IP входят в общий IP-элемент SRS независимо от DNS/sniffing, а также в отдельный набор WhatsApp и TXT.

Данные получены из расположения GitHub runner и Google Public DNS (с резервом Cloudflare). Региональные ответы на роутере могут отличаться; TTL не означает, что роутер обновляет SRS с той же частотой. Обновления сборки ежедневные, а интервал обновления SRS задаётся в AWGM. Добавление IPv6 в файл не включает его перехват или поддержку в туннеле.

Корпоративные сети Meta включены для широкого покрытия инфраструктуры; их необходимость для загрузки медиа не подтверждена. Отсутствие файла из чужого архивного списка не означает пробел: архивные 229 IPv4-записей WhatsApp уже покрываются BGP/custom. Полезная непокрытая запись `instagr.am` из старых правил добавлена в `custom-domains.txt`. Исторические широкие сети AWS/SoftLayer и Bintray не копируются автоматически.

### 6. Discord: голос, видео и TProxy

**Структура общего набора:** доменные условия и общие IP-сети находятся в отдельных элементах `rules`. Остальные два элемента содержат UDP-условия Discord. Для маршрутизации элементы набора работают как альтернативы: достаточно совпадения домена или IP, либо полного UDP-условия.

Разделение нужно также для DNS в AWG Manager. При `rule_set_ip_cidr_match_source: true` IP-условия проверяют адрес клиента. В sing-box 1.14.1 смешанный элемент добавляет к доменному совпадению обязательную проверку IP клиента и может отправить DNS-запрос через прямой резолвер. Отдельный доменный элемент позволяет выбрать DNS через VPN независимо от IP клиента. URL `routing.srs` и настройки AWGM остаются прежними; отдельные наборы мессенджеров используют такое же разделение. Локальная DNS-проверка в Actions сравнивает старый и новый формат на sing-box 1.12.12 и 1.14.1 без внешних DNS-запросов; компиляция SRS остаётся на закреплённой версии 1.12.12.

Для голосового трафика используются два отдельных элемента `rules`:

| Протокол | Порт назначения | IP-условие |
|---|---|---|
| UDP | `50000–65535` | Списки Discord IPv4 и IPv6 ITDog |
| UDP | `19000–20000` | `104.16.0.0/12`, только IPv4 |

Внутри каждого элемента условия **протокол + IP + порт** применяются одновременно. Эти сети не переносятся в общий список IP без ограничений портов.

Сборщик разбирает AST файла `convert.py` ITDog без исполнения его кода. Он проверяет структуру, UDP, допустимые диапазоны портов, имена источников подсетей и отдельную сеть Cloudflare. Исчезновение ожидаемых условий или изменение сети Cloudflare требует проверки и блокирует сборку.

Применение верхнего диапазона портов к IPv6 — допущение проекта: ITDog публикует IPv6-список, но его преобразователь использует IPv4. Для нижнего диапазона подтверждённого IPv6-правила нет.

Домены файлов и медиа покрываются доменными списками. Голосовое соединение к IP без доступного имени зависит от этих UDP-правил. Списки сообщества не гарантируют все текущие голосовые endpoints; общие сети могут захватывать чужой UDP на совпадающих портах.

В AWG Manager необходимо сохранить все условия rule-set, обеспечить определение домена через DNS/sniffing и проверить, что нужные UDP-порты не исключены из перехвата. Наличие IPv6 в SRS само по себе не включает перехват IPv6 на устройстве.

### 7. Что блокирует публикацию

Основные пороги задаются в [sources.json](config/sources.json):

| Проверка | Текущее условие |
|---|---|
| ITDog | Не менее 500 доменов |
| Итоговые доменные правила | От 500 до 100 000 записей suffix/exact |
| Общие IP-префиксы | Не более 20 000 после объединения |
| Изменение общего числа доменов или IP | От 80% до 150% предыдущего значения |
| Домены при появлении новых источников | Рост допускается до 300%; нижний порог сохраняется |
| IP при первом подключении новых Meta/CDN-источников | Рост до 20× прежнего числа; абсолютный предел 20 000 и нижний порог сохраняются. Последующие сборки снова ограничены 80–150% |
| Изменение BGP по каждому ASN | От 80% до 150% прежнего числа объединённых префиксов |
| Возраст резервного BGP-снимка | Не более 8 дней |
| Официальные CIDR Telegram | От 5 до 1000 префиксов, присутствуют оба семейства IP |
| Списки Discord | Непустой список каждого семейства, не более 2000 входных записей на семейство |

Публикацию также останавливают ошибки загрузки без допустимого резерва, некорректные домены/CIDR, неизвестный синтаксис V2Fly, потеря портовых условий Discord, ошибка компиляции, изменение правил после обратного преобразования или потеря проверяемого сервисного покрытия.

Пороги изменения размера сравнивают число записей. Они помогают обнаружить резкое изменение источника, но сами по себе не доказывают полноту покрытия.

### 8. GitHub Actions и расписание

Workflow: [.github/workflows/build.yml](.github/workflows/build.yml).

| Событие | Проверки | Публикация и Telegram |
|---|---|---|
| Ежедневный schedule, 20:17 UTC / 23:17 МСК | Полная сборка + свежесть публикаций ITDog | При успешной сборке |
| Ручной `workflow_dispatch` | Полная сборка | При успешной сборке в `main` |
| Push в `main` с изменениями `src`, `config`, `tests` или workflow | Полная сборка | При успешной сборке |
| Pull Request с такими изменениями | Тесты, сборка и проверка покрытия | Пропускаются |
| Изменение только README | Workflow не запускается | Пропускаются |

Для schedule проверяются последние плановые запуски ITDog **Create lists** и **Create subnets** в `main`. Оба должны успешно завершиться с начала текущей недели по UTC, после завершения должно пройти не менее 10 минут. При задержке следующая попытка выполняется следующим ежедневным запуском. Ручные сборки и push используют последнюю доступную версию без этой проверки свежести.

Автоматические коммиты результатов помечаются `[skip ci]`; изменения только `dist` не входят в пути запуска. Сборки выполняются последовательно, без отмены предыдущей. Лимит одного задания — 20 минут.

### 9. Отчёты, дельты и история

| Файл | Назначение |
|---|---|
| `dist/routing.json` | Итоговые правила в JSON |
| `dist/routing.srs` | Скомпилированный бинарный набор |
| `dist/routing.txt` | NDMS: домены с поддоменами и общие IPv4/IPv6-сети; комментарии о непереносимых условиях |
| `dist/report.md` | Читаемый отчёт: статус, источники, дельты, предупреждения |
| `dist/report.json` | Полные изменения, параметры результата и SHA256 JSON/SRS/TXT |
| `dist/tg_message.txt` | Текст сообщения для Telegram |
| `dist/source-snapshot.json` | Записи каждого источника для сравнения следующей сборки |
| `dist/whatsapp-dns.json` | Последние проверенные A/AAAA, TTL и статусы известных узлов WhatsApp/CDN |
| `dist/bgp-snapshot.json` | Сети, источники и исходные даты получения BGP |
| `dist/history.json` | Последние 52 успешные сборки |
| `dist/custom/` | Отдельные JSON мессенджеров |

Дельты итогового набора сравниваются с предыдущей успешной сборкой. Доменные условия, IPv4, IPv6 и портовые правила сравниваются отдельно. Дельты источников рассчитаны **до общего объединения**, поэтому их нельзя складывать для получения итоговой дельты.

Количество доменов в сводке — suffix и exact. Keyword/regexp показаны отдельно и также входят в список изменений. Число общих IP-префиксов не включает отдельные портовые правила Discord.

Тренд использует последние 7 успешных запусков, включая ручные. Это динамика запусков, а не календарных дней. Если прежнего снимка источника нет, показывается первый снимок без выдуманной дельты.

Успех без предупреждений отмечается зелёным, использование резервных BGP-данных — предупреждением, ошибка сборки — сообщением о сбое. Telegram показывает основные дельты и до 12 изменившихся источников; полные данные доступны в отчёте.

Для доставки задайте `TG_BOT_TOKEN` и `TG_CHAT_ID` в **Settings → Secrets and variables → Actions**. Без обоих значений уведомление пропускается. Шаг Telegram выполняется после сборки; его результат следует проверять отдельно от публикации.

### 10. Личные дополнения

`custom-domains.txt` — домен без протокола, пути и порта, одна запись на строку. Каждая запись включает поддомены. `custom-ip-cidrs.txt` — строгий CIDR; отдельный адрес задаётся как `/32` или `/128`. В этих списках поддерживаются пустые строки и комментарии после `#`.

Перед добавлением сравните запись с выбранными источниками. Совпадение по названию сервиса не подтверждает владельца домена или сети. Широкий родительский домен CDN и общая IP-сеть могут направить через VPN сторонний трафик.

Если upstream со временем покрывает личный домен, проверка выводит уведомление. Она не переписывает custom-файл автоматически; итоговый набор всё равно сокращает повторения.

### 11. Локальный запуск

Нужны **Python 3.12+**, доступ по HTTPS к источникам и официальный sing-box. Сторонние Python-библиотеки не требуются.

**Linux / macOS:**

```sh
python -m unittest discover -s tests -v
python src/install_sing_box.py
SING_BOX=.tools/sing-box python src/build.py
python src/check_service_coverage.py
```

**Windows PowerShell:**

```powershell
python -m unittest discover -s tests -v
python src/install_sing_box.py
$env:SING_BOX = "$PWD\.tools\sing-box.exe"
python src/build.py
python src/check_service_coverage.py
```

Установщик закрепляет sing-box **1.12.12** и проверяет архив по SHA256 релиза. Используется rule-set **version 1**. Обратное преобразование сравнивает содержимое правил, чтобы подтвердить сохранение условий.

Для проверки заранее полученных источников можно задать `SOURCE_CACHE`. Имена файлов — SHA256 URL с расширением `.txt`; `manifest.json` содержит `fetched_at` и массив `sources` с полями `url`, `sha256`. Возраст копии должен быть не более 24 часов, содержимое должно совпадать с SHA256. Этот механизм относится к загрузкам через `fetch()`; резервная таблица bgp.tools и установщик sing-box обращаются к сети отдельно. В обычном Actions кэш не используется.

### 12. Проверка на устройстве и откат

Сборка проверяет данные и формат, а фактическую работу проверяют на устройстве: загрузку SRS, выбранные сайты, вложения и звонки Discord, загрузки Nexus и IPv6. Роутер и сервер сборщик не перенастраивает.

Для быстрого отката верните прежний проверенный URL набора в AWG Manager. Для отката результата в репозитории восстановите согласованный комплект файлов `dist` из успешного коммита отдельным коммитом или отмените изменение, вызвавшее проблему. JSON, SRS и TXT должны соответствовать одному успешному запуску.
